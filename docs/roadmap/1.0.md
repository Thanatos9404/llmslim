# LLMSlim 1.0 roadmap

**Goal:** memory and context for AI agents with no LLM in the loop, deterministic, local and auditable, and stable
enough to depend on.

The three pillars:
- **Memory without extraction.** Keep what was said and select at read time. No model call to build memory, and no
  wrong extracted facts.
- **Cache-safe context for agent loops.** Keep the prompt prefix stable so provider prompt caches keep hitting. Never
  edit turns in a way a provider rejects. Stay under price cliffs. Report savings net of caching.
- **Trust boundaries.** Retrieved, remembered and tool text is data. It can never be promoted to instructions.

Status as of 29 October 2026, after 0.12.0. Releases: 0.10, 0.11 and 0.12 are out; 0.13 is the release candidate,
with the item H changes (including the Python 3.10 floor); then 1.0.0. Items are tracked as GitHub issues and pull
requests. Every quality change is chosen on development data and measured once on held-out test data, as in earlier
rounds.

The paid editions built on Core, LLMSlim Orbit (hosted, opening with 1.0) and LLMSlim Vault (self-hosted, formerly LLMSlim
Platform), have their own plan. Everything listed here ships in the MIT Core.

## Known quality issues to fix before 1.0

These were found while building the memory API. Each will be validated on development data before it ships.

- **Stemming missed common word forms** ("move" and "moved", "time" and "times", "shop" and "shopping"). Fixed in #57 (0.10.0),
  which is neutral within noise on the dev splits and better on LoCoMo. Derived forms such as "allergy" and "allergic"
  are left to semantic relevance.

The two issues below were first measured before 0.12.0 changed how a long history is read. They were measured again on
1 November 2026 against main (0.12.0 and the unreleased changes), on the development splits only: 308 LongMemEval
questions with labelled evidence and 230 LoCoMo questions, at 2,500 and 10,000 tokens. These are evidence measurements
with no model in the loop, not answer accuracy: the share of questions whose labelled evidence turns are all in the
selected context. Differences are paired, with bootstrap 95% intervals. LLMSlim was tuned on some of these LongMemEval
questions in earlier rounds, which if anything favours it.

- **The leftover budget might favour the oldest sessions** when little matches a question. Before 0.12, giving ties to
  the newest sessions changed no LongMemEval question and lost 0.4 points on LoCoMo at 2,500 tokens. On the 0.12 read
  path, giving the leftover top-up's ties to the newest turns again changes no LongMemEval question at either budget;
  LoCoMo moves by +0.4 points at both budgets (1 question up at 2,500; 3 up and 2 down at 10,000). Giving every tie in
  the selection to the newest turn rewrites 74 and 158 of the 308 LongMemEval contexts, but only one question loses
  evidence (-0.3 points at 2,500), and LoCoMo moves by 0.0 and +0.4. Neutral again, so nothing changes and this issue
  is closed.
- **Dense retrieval over turns is still ahead on LongMemEval.** On test it answered 80.6% to LLMSlim's 77.8% at 10,000
  tokens, before 0.12. On dev, the 0.12 read path keeps all the evidence for 89.6% of LongMemEval questions at 2,500
  tokens and 94.8% at 10,000, up from 61.0% and 88.6% for the earlier read path (whole sessions through
  `compress_documents`, as in the test run). The same dense retrieval (Qwen3-Embedding-0.6B) still keeps more: 93.8%
  and 97.7%, ahead by 4.2 points (1.0 to 7.5) and 2.9 points (0.3 to 5.8). The short gold answer is in the context as
  often for both (66.4% and 66.4% at 2,500, 70.6% and 71.1% at 10,000). On LoCoMo, dense retrieval is not ahead: -4.3
  points at 2,500 and +2.6 at 10,000, neither significant. A simple hybrid, lexical and dense candidates merged by
  reciprocal rank, is ahead of main on LoCoMo (+10.4 and +7.8 points) and at 10,000 on LongMemEval (+2.3), but behind
  dense retrieval on LongMemEval at 2,500 (-5.8). Rescoring main's own candidates with the same embedding model
  (`relevance=` a callable, already public) closes most of the LongMemEval gap (+2.3 and +1.9 points over main; 1.9
  and 1.0 behind dense retrieval, not significant) but loses 4.3 points on LoCoMo at 2,500 (-9.1 to +0.9). No variant
  is ahead everywhere, so the default stays lexical. Optional hybrid recall stays the candidate fix: it is chosen on
  dev, then confirmed once on fresh held-out questions with a reader, because the LongMemEval test split has already
  been read for three versions.
- **Two-person conversations keep less evidence on the 0.12 read path.** Found while measuring the above. On LoCoMo,
  with the first speaker stored as `user` and the second as `assistant`, main keeps all the evidence for 75.7% of
  questions at 2,500 tokens and 88.3% at 10,000, against 85.7% and 96.5% for the earlier read path (whole sessions
  through `compress_documents`, one "Speaker: text" line per turn): -10.0 points (-14.3 to -5.7) and -8.3 (-12.6 to
  -4.3). Storing both speakers as `user` recovers about half of that (81.3% and 93.0%). The largest cause was in
  ranking: a reply short enough to be one window inherited no relevance from its session, unlike a user turn, so a
  short reply that shares no word with the question waited for the leftover budget. Partly fixed in #136: 78.7% at
  2,500 tokens and 92.2% at 10,000 (+3.0 points, +0.4 to +6.1; +3.9, +1.3 to +7.0), with no loss on LongMemEval (89.9%
  and 95.1%). The date repeated on every kept turn took 21-22% of a LoCoMo context in labels. It is shown once per
  session in #137 (`date_format` defaults to `None`; `"%Y-%m-%d"` gives the old labels): labels drop to 9-11%, and
  LoCoMo reaches 80.0% and 93.5% (+1.3 points at both budgets, 3 questions up and none down) with no change on
  LongMemEval. That gain's interval touches zero, so it misses the pass rule and is not counted as a recall fix; the
  change was made for the label cost. The standing-requests section still opens 229 of the 230 LoCoMo contexts, with
  four sentences that are not requests ("Whenever I hear this jam, I think ...", "You never shy away ...", advice to
  the other speaker). Measured again after #137, it no longer costs evidence: turning the section off gives -0.4 points
  at 2,500 tokens (1 question up, 2 down) and 0.0 at 10,000. A narrower detector, under which a habit or a description
  of the listener is not a request, was measured and not shipped. It cuts the section to 81 of 230 LoCoMo contexts,
  with no change on LongMemEval, but it gives -0.9 points at 2,500 (2 questions down) through the same two questions.
  With about 30 more tokens of room, a longer relevant turn displaces shorter ones, among them the evidence. Still
  open: the rest of the gap to the earlier read path.

## What developers asked for (17 October 2026 research)

These are ranked by GitHub reactions and Hacker News points, and they set the order of the work above:
1. Long agent sessions lose work to context rot and compaction.
2. Prompt-cache breakage drives cost.
3. Long tool output fills the context.
4. Memory that writes wrong extracted facts.
5. Privacy and self-hosting.
6. Seeing what was in the context.

So:
- items B and E aim at coding agents first;
- MCP output compression is opt-in, because some MCP tools return live state, such as browser snapshots;
- every change keeps what the model has already seen byte-identical.

## Not in 1.0

- A generic compression gateway.
- The item F integrations (a LiteLLM guardrail, LiveKit Agents and Pipecat processors, a Cartesia Line example),
  which move to 1.x minor releases.
- More vendor integrations beyond those listed above.
- New learned-policy features.
